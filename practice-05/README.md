## Эксперимент с очередями

Прогноз: A → B → C → D → E → F. Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

A, B и C выполняются синхронно; D — обработчик уже выполненного Promise, E — продолжение после await. Они попадают в очередь микрозадач в этом порядке. Таймер F ждёт освобождения стека и обработки микрозадач; задержка 0 не означает немедленный вызов. При удалении обработчика D остальные метки сохранят относительный порядок.

В `examples/event-loop-own.js` после исходного примера зарегистрирована дополнительная микрозадача G. Прогноз: A → B → C → D → E → G → F. Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: собственная микрозадача
F: задача таймера
```

## Организация кода и HTTP-клиент

| Файл | Ответственность |
|---|---|
| api/server.mjs | Предоставленный учебный сервер. Не изменён. |
| src/api-client.js | URL, GET, заголовки, JSON, тайм-аут, отмена и ApiError. |
| src/task-api.js | Маршруты задач и категорий, нормализация фильтров и проверка схемы. |
| src/variant.js | Номер 8 и фильтры; без ветвления реализации по вариантам. |
| src/main.js | Консольный сценарий и сообщение об ошибке 404. |

`buildUrl` принимает абсолютный HTTP(S)-адрес без query и hash, убирает лишний разделитель пути и использует URLSearchParams. Пропускаются только undefined, null и пустая строка; false и 0 сохраняются. Входной query не меняется.

В `requestJson` отправляются GET и Accept: application/json. Отказ самого fetch обрабатывается отдельно от проверки response.ok. Поэтому полученный 404 остаётся HTTP-ошибкой. Успешный 204 возвращает null. У остальных успешных ответов проверяется Content-Type, затем разбирается JSON. Ошибка синтаксиса сохраняется как cause.

Таймер отменяет запрос через AbortController; внешний сигнал объединяется с ним через AbortSignal.any. Таймер очищается в finally. Передача fetchFn позволяет проверять ответы и ошибки без настоящей сети.

## Доменный модуль

Разрешены completed, priority, categoryId и q. q очищается через trim. Неверные типы и неизвестные параметры отклоняются до запроса. У задачи проверяются положительные безопасные id/categoryId, строка title длиной 1–100 после trim, логический completed и один из трёх приоритетов. У категории — id и name. В коллекциях проверяются уникальность id и равенство meta.total длине data.

## Последовательное и параллельное ожидание

Для двух независимых `/debug/delay?ms=80` выполнено три пары измерений.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс |
|---|---|---|---|
| Два await | 166.1 | 166.3 | 165.5 |
| Promise.all | 84.2 | 83.2 | 82.7 |

Последовательный вариант складывает ожидания; параллельный ждёт наиболее медленный из двух независимых ответов. Значения относятся к этому локальному запуску. Искусственных задержек в рабочем клиенте нет. Promise.all передаёт отказ одного запроса вызывающему коду, но сам не отменяет второй запрос.

## Отладка

Через Node inspector установлены настоящие точки останова до fetch, после Response, перед response.json() и при разборе HTTP-ошибки.

| Проверяемое значение | Успешный запрос | Ошибочный запрос |
|---|---|---|
| Путь | /tasks?completed=false&priority=high | /tasks/999 |
| status / ok | 200 / true | 404 / false |
| Content-Type | application/json; charset=utf-8 | application/json; charset=utf-8 |
| payload | data с id [4, 13, 34], meta.total=3 | error.code=TASK_NOT_FOUND, details={id:999} |
| Результат | JSON передан предметному модулю | ApiError: kind=http, status=404, code=TASK_NOT_FOUND |

URL на точках останова использовал временный порт 61315. `response.ok` проверяется до разбора успешного тела. Обработчик fetch не перехватывает созданную позднее HTTP-ошибку как network.
